ຍິງ Webhook ກັບຄືນໄປຫາ POS

POS ບໍ່ມີສ່ວນກ່ຽວຂ້ອງກັບການສະແກນຝ່າມືຫຼືການຕັດເງິນໂດຍກົງ — ໜ້າທີ່ຂອງ POS ມີແຕ່ (ກ) ບອກຈຳນວນເງິນທີ່ຈະເກັບ ແລ້ວໃຫ້ເຄື່ອງ terminal ເປີດໜ້າສະແກນຂຶ້ນເອງ ແລະ (ຂ) ລໍຮັບການແຈ້ງຜົນເມື່ອຈ່າຍສຳເລັດ

ສິ່ງທີ່ຕ້ອງກະກຽມ

  1. ບັນຊີຮ້ານ (Shop) — ສະໝັກ/ເຂົ້າສູ່ລະບົບແລ້ວທີ່ bio-payment-api
  2. ເຄື່ອງ terminal ທີ່ provision ແລ້ວ — ແອັບ shop-terminal ຢູ່ເຄື່ອງ F310P ຕ້ອງ login ເຂົ້າຮ້ານນີ້ແລ້ວຢ່າງໜ້ອຍໜຶ່ງເທື່ອ (ລະບົບສ້າງ credential ໃຫ້ອັດຕະໂນມັດຕອນ login)
  3. Device ID ຂອງເຄື່ອງ terminal — ເບິ່ງໄດ້ຈາກໜ້າ About this shop ໃນແອັບ shop-terminal (ຊ່ອງ “Device ID”) ເປັນຄ່າຄົງທີ່ຕໍ່ເຄື່ອງ ບໍ່ປ່ຽນແມ່ນລົບແອັບ/login ໃໝ່
  4. ປາຍທາງຮັບ Webhook (webhookUrl) — URL ຝ່າຍ POS ທີ່ເປີດຮັບ POST ຈາກອິນເຕີເນັດໄດ້ (ຕ້ອງເປັນ HTTPS ໃນລະບົບຈິງ)

ການຢືນຢັນຕົວຕົນ

ລະບົບມີ credential ສອງລະດັບທີ່ບໍ່ກ່ຽວຂ້ອງກັນ ໃຊ້ຄົນລະໜ້າທີ່ກັນຢ່າງຈະແຈ້ງ:

Credentialໃຊ້ເຮັດຫຍັງສົ່ງແບບໃດ
Shop JWT ຕັ້ງຄ່າໂປຣໄຟລ໌ຮ້ານ / webhook ເທົ່ານັ້ນ Authorization: Bearer <token>
X-Device-Id ສັ່ງເປີດໜ້າສະແກນຈ່າຍເງິນ (POST /palm/payment-intents ເທົ່ານັ້ນ) Header X-Device-Id: <deviceId>
⚠️ X-Device-Id ບໍ່ແມ່ນ secret

deviceId ເປັນຄ່າທີ່ສ້າງຢູ່ຝ່າຍເຄື່ອງ terminal ເອງ ບໍ່ໄດ້ຖືກເກັບເປັນຄວາມລັບ ແລະ ບໍ່ມີການກວດລະຫັດຜ່ານໃດໆເພີ່ມ — ຜູ້ໃດກໍ່ຕາມທີ່ຮູ້ຄ່ານີ້ ສາມາດສັ່ງເປີດໜ້າສະແກນຂອງເຄື່ອງນັ້ນ ດ້ວຍຈຳນວນເງິນທີ່ກຳນົດເອງໄດ້ (ເປັນການລົບກວນ ບໍ່ແມ່ນການຂະໂມຍເງິນ ເພາະການຕັດເງິນຈິງຍັງຕ້ອງຜ່ານ ການສະແກນຝ່າມື + consent ຂອງລູກຄ້າຢູ່ເຄື່ອງສະເໝີ) ໃຊ້ສະເພາະໃນລະບົບ POS ທີ່ເຊື່ອຖືໄດ້ ແລະ ເກັບ ຄ່ານີ້ຄືກັບຂໍ້ມູນພາຍໃນ ບໍ່ເຜີຍແຜ່ສູ່ສາທາລະນະ

ທາງເລືອກທີ່ປອດໄພກວ່າຄືໃຊ້ X-Terminal-Key (ຄີຍ໌ເຕັມຂອງເຄື່ອງ ເກັບເປັນຄວາມລັບແທ້ ຄັດລອກໄດ້ຈາກໜ້າ About ຂອງແອັບ shop-terminal ເຊັ່ນກັນ) — ຖ້າ POS ສາມາດເກັບຄວາມລັບໄດ້ຢ່າງ ປອດໄພ ແນະນຳໃຫ້ໃຊ້ອັນນີ້ແທນ X-Device-Id

ຕັ້ງຄ່າ webhookUrl / callbackUrl

webhookUrl ຄືປາຍທາງທີ່ bio-payment-api ຈະຍິງ callback ການຈ່າຍເງິນສຳເລັດໄປໃຫ້ ສ່ວນ callbackUrl ຄື URL ຂອງຝ່າຍ POS ເອງ (ເຊັ່ນ ໜ້າ “ຂອບໃຈທີ່ໃຊ້ບໍລິການ”) — ລະບົບບໍ່ໄດ້ ໃຊ້ຄ່ານີ້ເຮັດຫຍັງເລີຍ ພຽງແຕ່ແນບໄປກັບທຸກ webhook payload ເພື່ອໃຫ້ POS ຮູ້ວ່າຈະ redirect ລູກຄ້າໄປ ບ່ອນໃດຕໍ່

POST /api/v1/palm/payment-intents X-Device-Id ຫຼື X-Terminal-Key

ກຳນົດຈຳນວນເງິນທີ່ຈະເກັບ ແລ້ວສັ່ງໃຫ້ເຄື່ອງ terminal ຂອງຮ້ານເປີດໜ້າສະແກນຈ່າຍເງິນຂຶ້ນມາເອງ (ຜ່ານ realtime push ໄປທີ່ເຄື່ອງນັ້ນໂດຍກົງ)

Request

Fieldຊະນິດຄຳອະທິບາຍ

currencystringລະຫັດສະກຸນເງິນ ISO-4217 3 ໂຕອັກສອນ ເຊັ່ນ LAK

↻ ສົ່ງ orderNo ຊ້ຳໄດ້ — ປອດໄພສຳລັບການ retry

ຖ້າເນັດຂາດກາງທາງ ແລະ POS ບໍ່ແນ່ໃຈວ່າຄຳຂໍກ່ອນໜ້ານັ້ນສຳເລັດຫຼືບໍ່ ສາມາດຍິງຊ້ຳດ້ວຍ orderNo ເກົ່າໄດ້ທັນທີ — ຖ້າລາຍການເກົ່າຍັງບໍ່ຈົບ (ລໍສະແກນ/ກຳລັງສະແກນຢູ່) ລະບົບຈະ ສົ່ງ intentId ເກົ່າກັບຄືນມາ ("replayed": true) ແລະ ເປີດໜ້າສະແກນຊ້ຳໃຫ້ ອີກຄັ້ງ ແທນການສ້າງລາຍການໃໝ່ຊ້ອນກັນ ແຕ່ຖ້າລາຍການເກົ່າຈົບໄປແລ້ວ (ຈ່າຍສຳເລັດ/ຖືກຍົກເລີກໄປແລ້ວ) ການສົ່ງ orderNo ເກົ່າຊ້ຳຈະໄດ້ error 409 ORDER_NO_ALREADY_USED ແທນ — ອໍເດີໃໝ່ຕ້ອງໃຊ້ orderNo ໃໝ່ສະເໝີ

intent ຈະໝົດອາຍຸໃນ expiresInSeconds (ປົກກະຕິ 5 ນາທີ) ຖ້າບໍ່ມີໃຜສະແກນພາຍໃນ ເວລານີ້ ລາຍການຈະຖືກຍົກເລີກອັດຕະໂນມັດ ແລະ ຈະບໍ່ມີ webhook ໃດໆສົ່ງມາ — ຝ່າຍ POS ຄວນມີ timeout ຂອງຕົນເອງທີ່ໃກ້ຄຽງກັນ ແລ້ວຖືວ່າລາຍການນັ້ນ "ບໍ່ສຳເລັດ" ຫາກບໍ່ໄດ້ຮັບ webhook ພາຍໃນເວລາທີ່ກຳນົດ

POST <webhookUrl ທີ່ຕັ້ງໄວ້> ຍິງມາຈາກ bio-payment-api

ເມື່ອລູກຄ້າສະແກນຝ່າມື ແລະ ຕັດເງິນສຳເລັດ ລະບົບຈະ POST ໄປທີ່ webhookUrl ທີ່ຕັ້ງໄວ້ແບບ fire-and-forget — ຍິງຄັ້ງດຽວ ບໍ່ມີການ retry ຫາກປາຍທາງລົ້ມ ຫຼື ຕອບຊ້າ ແລະ ການສົ່ງ webhook ບໍ່ກະທົບຜົນການຕັດເງິນທີ່ເຄື່ອງ terminal ແຕ່ຢ່າງໃດ (ເງິນຖືກຕັດໄປແລ້ວ ບໍ່ວ່າ webhook ຈະສົ່ງສຳເລັດຫຼືບໍ່)

app.post('/webhooks/bio-payment', (req, res) => {
  const signature = req.headers['x-webhook-signature'];
  const expected = crypto
    .createHmac('sha256', WEBHOOK_SECRET)
    .update(req.body) // req.body ຄື Buffer ດິບ
    .digest('hex');

  if (!crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected))) {
    return res.status(401).send('invalid signature');
  }

  const payload = JSON.parse(req.body);
  // ... ບັນທຶກຜົນການຈ່າຍເງິນຂອງ orderNo ນີ້ ແລ້ວຕອບ 200 ກັບໄປ
  res.status(200).send('ok');
});
